## 4. 障害時の切り戻し

### 4-0. 先に決める: どの対応をするか

| 状況 | まずやること |
|---|---|
| AIの暴走・想定外の自動動作・費用の急増 | **§5 緊急停止**（デプロイの切り戻しは不要） |
| 公開した変更が原因で画面／APIが壊れた | **§4-1 Render で前のデプロイに戻す** |
| DBのマイグレーションが原因 | **§4-2** を先に読む（コードを戻すだけでは直らない） |
| 個人情報が見えている・漏えいの疑い | まず被害を止める（該当機能を止める／切り戻し）→ §6 の連絡 → 弁護士へ |

### 4-1. Render で前のデプロイに戻す（バックエンド／フロント共通）

> **この手順は、Render の公式ドキュメント（Rollbacks）で、公開前に画面と一致するか確認してください。**
> この文書の作成時は外部ドキュメントを取得できなかったため、操作名は一般的な画面構成に基づく記述です（要確認）。

1. Render ダッシュボード → 対象のサービス（`awp-backend` または `awp-frontend`）を開く。
2. 「Events」または「Deploys」の履歴から、**問題が出る前に成功していたデプロイ**（T-1日にメモしたコミット）を探す。
3. そのデプロイの操作メニューから **Rollback**（前のデプロイに戻す）を選び、確認する。
4. ロールバック後は、Render の仕様として **自動デプロイが止まる場合があります**（要確認）。止まっている場合、`main` に新しいコミットが入っても反映されません。原因を直すまでそのままにし、直したら自動デプロイを再度有効にします。
5. `GET /api/health` の `commit` が戻したコミットと一致することを確認する。
6. 原因の修正は、ブランチ → PR → 運営者のマージで行う（`main` へ直接プッシュしない）。

バックエンドとフロントは別サービスです。API の形が変わった変更を片方だけ戻すと食い違うので、**変更が両方にまたがっていたら両方戻します**。

### 4-2. データベースの変更がある場合（重要）

- バックエンドは起動のたびに `prisma migrate deploy` を実行します（`backend/start.js`）。
- **Render のロールバックはコードを戻すだけで、すでに適用されたマイグレーションは戻りません**（Prisma に自動のダウン処理はありません）。
- そのため、次のルールにします。
  1. 公開に含まれるマイグレーションは、**古いコードでも動く（列の追加のみ・既存を壊さない）** ことをデプロイ前に確認する。
  2. 列の削除・型の変更など戻せない変更は、公開のタイミングに混ぜない（別の日に段階的に）。
  3. データが壊れた場合は、Render の PostgreSQL の復元機能（S17 で確認したもの）で復元する。復元は **復元時点以降のデータを失う** ので、必ず運営者が判断する。
- 復元・マイグレーションの手動操作は、実行前に **影響範囲を書き出して** 【責任者名】の承認を得る。

### 4-3. 切り戻し後の確認

- `GET /api/health`、ログイン、公開ページ、予約リクエスト、`/admin`
- 切り戻しの間に作られたデータ（登録・予約・注文・振込）に不整合が無いか。ある場合は一覧にして運営者へ
- 利用者へのお知らせ（必要なら）。文面は運営者が書く: 【お知らせ文】

## 5. 緊急停止の使い方

### 5-1. 画面から止める

1. 運営者（管理者アカウント）でログインし、`/admin/emergency`（管理画面の「緊急コントロール」）を開く。
2. 止めたい項目の「止める」→ 確認の「止める」を押す。**押した直後に本番へ反映**されます（`PUT /api/ops/emergency`、管理者のみ）。
3. 表示が「停止中」（赤）になったことを確認する。再開は同じ画面の「再開する」。

| スイッチ（`SystemSetting` のキー） | 止まるもの | 止まらないもの |
|---|---|---|
| AIエージェントの定期実行（`pause_agent_loop`） | 6時間ごとのマーケティング・成長分析・監視・自己PRなどのエージェント | ユーザーが画面から押すAI機能（ページ作成・チャットボット・LINE自動応答 など） |
| SNSの予約投稿（`pause_sns_posting`） | 予約済みSNS投稿の送信（予約は消えず、再開すると順に投稿） | 下書きの作成 |
| ローンチ・クルー（`pause_crew`） | Discordでの進行・GitHubへの実装依頼 | すでに動き出した Claude Code の作業は止まらない場合がある（要確認） |
| AI企業（`pause_company`） | CEO以下の自律運営（日次の経営サイクル・タスクの実行）。管理画面の開始操作は停止中だと 409 で拒否される | 承認待ちの操作（そのまま残る） |

- AIオペレーター（`/admin/ops` のチャット）からも「止める」提案ができますが、**提案を運営者が承認したときだけ**反映されます。緊急時は上の画面から直接操作してください。
- AI企業は、初期データの作成時に `pause_company = true`（停止）で始まります（`backend/src/company/seed.ts`）。公開前に意図した状態か確認してください。

### 5-2. 緊急停止スイッチが **ない** もの（ここは切り戻し／環境変数で対応）

| 止めたいもの | 手段 |
|---|---|
| 新規登録・ログイン全体 | 専用スイッチは無い。バックエンドのデプロイを切り戻す、または Render でサービスを一時停止（Suspend）する（要確認） |
| ページのAIチャットボット／LINE自動応答／ページ作成のAI | 専用スイッチは無い。`ANTHROPIC_API_KEY` を Render で外して再起動すると、AIを使わない動作（チャットボット：「いまはAIが使えません」、LINE応答：定型文）になる |
| 特定のページ／プロフィール／投稿 | 管理画面「通報」から非公開にできる |
| SMSの大量送信 | `SMS_GLOBAL_HOURLY_LIMIT` を下げる（再デプロイ）／Twilio側の制限 |
| お金の動き（収益の記録・キャッシュ） | 台帳は書き換えず逆仕訳で戻す（`/api/wallet/admin/revenue/:id/reverse`）。出金は元々できない |

> 「止める」ためのコードは、将来スイッチを追加する場合も既定を「動く」にし、人が操作したときだけ止める形にします。

## 6. 既知の注意点（公開前に必ず読む）

コードを読んで見つけた、公開前に判断が必要な点です（推測ではなく実装の記述）。

1. **アカウント削除が失敗する可能性**: `DELETE /api/auth/account`（`backend/src/routes/auth.ts`）は、問い合わせ・ページ・LINE連携・ユーザーだけを削除します。一方、`SocialAccount` `ScheduledPost` `AgentTask` `AutomationWorkflow` は `User` への外部キーが `ON DELETE RESTRICT`（マイグレーション参照）で、これらのデータが残っているユーザーでは削除が外部キー違反で失敗する可能性があります（`LandingPage` / `LineConfig` は先に削除している）。App Store / Google Play の必須要件なので、**公開前にQ12を必ず通し、失敗するなら別PRで修正**してください。この文書の作成では修正していません（依頼の範囲外）。
2. **プライバシーポリシーとの差**: ポリシーは「アカウント削除で関連データを削除」と書いていますが、台帳（`LedgerEntry` の `userId` は外部キーなし）や `RevenueEvent` などの会計記録、`AffiliateClick` は削除対象に入っていません。弁護士に確認する論点です（`legal-brief.md` §10）。
3. **平文保存**: LINEのチャネルシークレット／アクセストークン（`LineConfig`）、SNS連携のトークン（`SocialAccount`）は平文です（`schema.prisma` のコメント「フェーズ2で対応」）。暗号化されているのは、Harness の APIキー、出品者・AWPの振込先口座、Discord Webhook です（`secretBox.ts`）。
4. **自動削除のタイミング**: 予約リクエストとチャットボットの質問の「期限切れ削除」は、そのページに新しい予約／質問が届いたときに実行されます（定期ジョブではない）。ショップの注文は10分ごとの掃除で削除されます。
5. **回数制限はメモリ上**: 再起動でリセットされます（§3 の補足）。
